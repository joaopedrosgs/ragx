# Native acceleration study

This note records where C++ can shorten the Godot map export without moving
pipeline policy, cache ownership, or file publication out of Python.

## Measured baseline

The full benchmark used the LATAM client on Windows with 12 logical CPUs and no
Godot import. It exported all 939 maps into a new directory.

| Implementation | Workers / budget | Cold | Warm | Peak private memory |
|---|---:|---:|---:|---:|
| Original Python | 2 / 4 GiB | 1,274.719 s | 271.875 s | 1,788.3 MiB |
| Parse-reuse Python | 6 / 6 GiB | 385.906 s | 81.281 s | 4,577.0 MiB |

The optimized cold pass completed all 939 maps with zero failures and produced
38,171 files / 6,038,596,003 bytes. This is 3.3x faster than the original
baseline. The warm pass still changed 17 files, so cache invalidation and shared
output ownership remain open work.

A single-worker cold profile used five representative, model-heavy maps:
`prontera`, `malaya`, `eclage`, `prt_mk`, and `1@face`. Before changing code it
took 47.562 s. GND was parsed once for terrain and again for water; GAT was
parsed separately for the debug PNG, runtime binary, and sometimes effect
heights. Retaining one parsed RSW/GND pair and one parsed GAT per map reduced the
same export to 36.546 s, with the same 1,466 files and 118,657,917 bytes. That is
a 23% cold improvement without native code. The warm sample fell from 11.391 s
to 6.922 s.

## Remaining profile after parse reuse

The 36.5-second profile has overlapping cumulative times, so rows cannot be
added together.

| Area | Cumulative time | Native opportunity |
|---|---:|---|
| Model builds | 14.6 s | Medium: fuse RSM mesh baking and smoothing |
| Texture conversion | 8.4 s | Low to medium: Pillow already owns decode/encode |
| Terrain build | 6.5 s | High: Python loops assemble every surface vertex |
| Shared texture/file publication | 5.6 s | Low: mostly filesystem work |
| Magenta key | 4.4 s | Medium: first try a better NumPy formulation |
| PNG encode | 3.4 s | Low: already native Pillow code |
| Model mesh bake | 2.7 s | High within model work |
| GAT parse | 2.4 s | High only if parsing stays fused with its consumer |
| GND parse | 1.9 s | High only if parsing stays fused with terrain creation |
| GRF decrypt | 2.0 s | Medium, but smaller than mesh work |
| GRF table parse | 2.0 s | Low: paid once per worker, not once per map |

Returning millions of Python tuples from a C++ parser would preserve much of
the allocation cost. The native boundary should therefore be the complete
per-map compiler. It accepts archive-backed RSW/GND/GAT/RSM/texture inputs and
emits ready-to-publish scene, glTF, binary, texture, and navigation artifacts.
Parsing, terrain/model mesh construction, normal smoothing, colour keying, and
buffer serialization remain inside C++ without per-vertex Python objects.

The scheduler must construct a deduplicated asset graph before conversion:
unique models and textures compile once, then map jobs reference their results.
The current process-per-map design lets workers discover and build the same
popular model simultaneously; a faster implementation must not reproduce that
contention. Python remains responsible for the CLI, engine exporter selection,
generated-code orchestration, progress, and final atomic publication.

## Proposed order

1. Keep parse reuse and make shared publication reliable at high worker counts.
2. Build a discovery pass that resolves map dependencies into unique terrain,
   model, texture, water, and navigation jobs before conversion begins.
3. Implement a C++17 `ragx_native` core for GRF reads/decryption, map/model
   parsing, texture colour keying, mesh generation, smoothing, and binary/glTF
   buffer emission. Expose coarse batch calls through pybind11 rather than
   crossing the boundary per asset or vertex.
4. Bind with scikit-build-core, publish prebuilt wheels with cibuildwheel, and
   retain Python as the executable specification and source-install fallback.
5. Run native and Python implementations against the same fixture corpus and
   compare every generated byte before making native the default.

Do not move command parsing, engine selection, incremental-cache policy, scene
text generation, or publication into C++. Those parts change frequently and do
not dominate CPU time.

## Acceptance gate

A native backend is worth making the default when it meets all of these
conditions:

- 3-5 minute cold export for all 939 maps on the benchmark machine, with a hard
  upper gate below the 385.906-second optimized Python baseline;
- byte-identical generated assets, apart from explicitly reviewed stable
  serialization changes;
- the complete Python test suite passes against both native and fallback paths;
- corrupt and truncated inputs fail with the same public exceptions;
- wheels cover supported Windows, Linux, and macOS CPython versions;
- a source checkout without a compiler still runs through the Python fallback.

The 3-5 minute target requires both compiled kernels and graph-level
deduplication. A narrow parser extension is not expected to reach it. The
38,171-file, 5.62-GiB output also imposes a filesystem/encoding floor, so every
native milestone must be measured on the full export rather than extrapolated
from microbenchmarks.
